TNS-MES 架构优化方案

分析日期 2026-09-16 · 基于本地代码 D:\TNS-MES + 生产数据库实查（tns_mes @ 10.30.10.141）

0 · 服务拓扑现状

K8s × 2 副本应用服务器 10.30.10.140 · tns-mes-backend v32
SQL Server数据库服务器 10.30.10.141 · tns_mes 库 37 表
SAP 测试租户my200683 · Basic Auth · 200+ 产品
中间件默认关闭RocketMQ/Sentinel/Nacos/Seata 特性开关
拓扑含义：双 Pod 并行 → 一切定时任务必须加分布式锁；独立 DB 服务器、连接池仅 20 → 事务内不得做外部 IO；中间件可随时不可用 → 集成层需可降级。以下问题按此原则排序。

1 · 数据库架构（实查证据）

P0 大字段内联，主表膨胀严重

实测行均 payload：prd_work_order 47KB/行（最大 180KB）——600 行占 20MB；qa_batch 12.7KB/行；product 9KB/行（1849 行含 payload）。sap_payload nvarchar(max) 内联在聚集索引中，全表扫描/统计信息/备份全部被拖慢。

✎ 方案：建 int_sap_payload(entity_type, entity_id, payload, fetched_at) 独立表，主表去除 nvarchar(max)；同步时按需回查，列表/报表零开销。

P0 Outbox 已发布消息从不清理

实测 mes_outbox_message 存量 12195 行，其中 PUBLISHED 状态 4065 条（最旧 2026-09-03），发布成功后永久滞留，表持续线性增长。

✎ 方案：新增定时清理（PUBLISHED 且 7 天前 → 删除，每次限 500 批删）；或 V23 中预留的归档机制补上执行 job。同时需分布式锁防双 Pod 并发清理。

P1 product 表 114 列，SAP 自定义字段平铺

YY1_F_* 等 SAP 租户自定义字段（约 40 个）直接平铺进主表，prd_work_order 也达 83 列。列数膨胀 → 每行定长部分变大、维护成本高、与 SAP 租户字段耦合。

✎ 方案：垂直拆分 product_sap_ext(product_id, 字段…)；主表保留 MES 业务字段 + 常用 SAP 字段。列表页只查主表。

P1 API 日志整包响应入库

int_api_call_log.response_body 单条最大 20000 字符（截断值过高），462 行已占 3.5MB，长期跑全量同步会快速膨胀。

✎ 方案：截断至 2000 字符 + 保留天数 30 天定时清理；或与 payload 一样移入旁表。

P1 热表索引不足

eng_bom_item（7698 行/66 列）和 prd_work_order_operation（3285 行）各只有 2 个索引；BOM 展开、工序查询是高频路径。

✎ 方案：补 eng_bom_item(bom_id, material_code)、prd_work_order_operation(work_order_id, seq) 复合索引；配合大字段移出后重建聚集索引回收空间。

P2 领域表归属错位（空表可低成本纠正）

qua_inspection/qua_inspection_item 等 12 张表为 0 行，但 Java 侧 QualityInspection 实体却在 execution 模块；qa_batch 仅存 productCode/productName 字符串，与 product 无外键。

✎ 方案：趁数据为空，把质检实体迁入 quality 模块；qa_batch 增 product_id 外键（有数据后做 RID 回填，成本即刻最低）。

2 · 后端架构

P0 大事务包裹 SAP HTTP 调用

SapSyncService.java:106/292 的 @Transactional 覆盖"多页 SAP 拉取 + 逐行落库"全过程；WorkReport/GoodsReceipt/MaterialIssue 三个 Service 的 post() 同样在持锁事务内调中间件 HTTP（read-timeout 30s）。DB 连接池仅 20，一次慢同步可耗尽全部连接，拖垮整个集群。

✎ 方案：改为"无事务拉取全量数据 → 分块(如 200 行/批)短事务落库"；post() 拆两段：本地状态变更先提交，HTTP 调用移出事务，失败走补偿/重试队列。

P0 定时任务多副本竞态

SapSyncScheduler.java:20,30 仅用 JVM 内 AtomicBoolean 防重入；SyncJobService.java:139-142 用 check-then-set 判重。双 Pod 下同一同步任务会并发执行两次（曾有 outbox 双 Pod 抢占问题的前车之鉴，但 DistributedLockService 只有 OutboxPublisher 在用）。

✎ 方案：Scheduler / SyncJobService / 新增的 outbox 清理 job 全部用现有 DistributedLockService（Redis Lua 原子锁 + renew）包裹。

P1 SapSyncService 巨类（1134 行 / 约 40 方法）

单类混装 HTTP 客户端、OData 解析（text/decimal/bool/date 15 个工具方法）、5 类实体映射与 upsert 编排。上次 to_BasicText→to_ProductBasicText 就改了 4 处，改一处漏三处。

✎ 方案：拆为 ODataClient(分页/认证) / ODataRowParser(类型转换) / ProductMapper、WorkOrderMapper、BatchMapper、CustomerSupplierMapper / SyncOrchestrator(编排+短事务)。

P1 同步 N+1 + BOM 删重建

循环内逐行 findByCode（SapSyncService.java:154）；BOM/工艺路线每次同步整组 DELETE 后 INSERT（659/673/737/822/873 逐行 saveAndFlush）——7698 行 BOM item 全量同步时写放大严重，这也是当初唯一约束冲突的根源。

✎ 方案：先 findByCodeIn(codes) 一次性载入 Map；BOM 改差量更新（比对 itemKey 集合，只删消失项/更新变更项/插入新增项）。

P1 post() 过账模板三处复制

WorkReportService:77-111 / GoodsReceiptService:96-135 / MaterialIssueService:87-108 近乎逐行重复（构建凭据→HTTP→结果处理）。

✎ 方案：抽取 SapPostingService.post(docType, payload) 统一模板，三处各留差异参数。

P2 配置硬编码与弱口令

application.yml:139,191 admin-password: admin123；application-prod.yml:79-80,98-99 nacos/nacos；中间件 IP、SAP 租户 URL 写在默认配置中；prod actuator show-details: always。

✎ 方案：全部改环境变量注入（K8s Secret 已有先例），prod 收紧 actuator 暴露。

P2 其他

  • web 层跨模块注入：production\web\WorkOrderController.java:30-31 直接注入 ProductRepository，绕过 service；
  • 命名不一致：integration 用 sap\repository，其余模块用 repo；
  • 状态机魔法字符串（"DRAFT"/"RELEASED"）散落 service，枚举仅当默认值用；
  • 关键字搜索 Specification.where(null) 样板在 7 个 service 重复 → 抽 BaseSpecificationHelper。

3 · 前端架构

P1 main.js 成为上帝处理器（317 行）

单个全局 click 委托承载全站 50+ 业务 action 分支；分页 loader 映射表重复 3 次。新增页面必须改入口文件，回归风险集中。

✎ 方案：action 分发下放各 view（view 返回自己的 handler 注册表），main.js 只保留路由/认证壳层。

P1 突尼斯用户会看到中文

ar-TN.js 仅 217 key（zh/en 各 296），缺 79 个——含全部 status.* 状态翻译与 40+ 产品自定义字段；fallback 是 zh-CN。阿语用户界面直接出现中文。

✎ 方案：以 en 为基准补齐 ar-TN 79 key；fallback 链改 ar-TN → en。

P2 其他

  • 19 处手写抽屉表单 → 抽 formField/multiLangField 组件（nameZh/nameEn/nameAr 三元语模式重复 5 次）；
  • request.js:35 401 过期跳登录却提示"用户名或密码错误"；无超时/AbortController；
  • menuConfigs 缓存无失效机制，改配置后旧缓存持续生效；
  • 行内 closest('tr').querySelector('.code') 反模式出现约 15 次。

4 · 实施路线图

1
P0 稳定性（预计 1-2 天，改动小、收益大）
  • 定时任务套分布式锁（Scheduler + SyncJobService）
  • SAP 同步事务边界重构：无事务拉取 → 分块短事务落库
  • Outbox 清理 job（PUBLISHED 7 天 + 批删 500）+ API 日志截断 2000 字符
2
P1 结构优化（预计 3-5 天）
  • Flyway V28：sap_payload 移旁表 + 迁移存量数据 + 热表补索引
  • SapSyncService 拆分（ODataClient/Parser/Mapper/Orchestrator）+ N+1 批量化 + BOM 差量更新
  • post() 模板合并；前端 action 下放 view + ar-TN 补齐 79 key
3
P2 治理项（随迭代消化）
  • product/product_sap_ext 垂直拆分；quality 模块领域归位
  • 配置环境变量化（admin/nacos 弱口令）；actuator 收紧
  • 前端表单组件抽取、401 提示修正、menuConfigs 失效机制
每阶段独立可发布、可回滚；Phase 1 不动表结构（纯代码），Phase 2 的 Flyway 迁移已考虑 SQL Server 批编译坑（ALTER 与 UPDATE 分批执行）。建议按 Phase 顺序实施，Phase 1 完成后即可消除当前最大的稳定性风险。
